Before you start

The one idea that makes all of this click

Fine-tuning changes a model's behaviour — its voice, format, and style. It does not teach the model facts. Hold this the whole way through; every step below is built on it.

◆ Behaviour vs. facts

Behaviour → train it in. "Always answer in warm, second-person JSON" is stable. Safe to bake into the weights.

Facts → keep in the prompt. "Payout is 48 hours", "we cover 6 cities" — these change. Bake them into weights and the model will confidently repeat the stale value forever.

The test: if it could change next quarter, would a trained-in version become a lie? If yes → prompt, not weights.

◆ What to look for

Read the output critically. Is it valid JSON? Does the voice sound generic — "Join our team of dedicated professionals!" — rather than a distinct brand? Did it get the brand name slightly wrong, or invent a fact you never gave it? Those flaws are exactly what training will fix.

Part 2 · the trick

You train ~1% of the model

Full fine-tuning is too big for a free GPU. QLoRA is two hacks stacked: freeze the giant base model and train a tiny overlay (LoRA — like a git-diff over a frozen image), and store the frozen base in 4-bit to save memory. Let's see how little you actually train.

You should see something like
trainable params: 18,464,768 || all params: 1,562,179,072 || trainable%: 1.18
◆ Read the number

You're steering a 1.56-billion-parameter model by training ~18 million of them — just over 1%. The other 99% stays frozen. The knob r=16 sets the overlay size; bigger r = more capacity but overfits faster on small data.

Part 3 · the real work

Give it examples to learn from

Fine-tuning isn't instructions — it's worked examples. The model copies the output field, so you must own that field: it has to be the gold standard, better than what the base model produces on its own.

▲ The iron law of datasets

Never let the model write its own training outputs. If you train it on its own generic output, you teach it to be generic forever. A human who knows the target voice writes or approves every output.

3

Create a tiny gold dataset

3 examples — enough to see the mechanism
▸

Three hand-written examples. Notice two things: the voice is consistent and specific, and each output only uses facts from its own input. Swap in your own brand/voice later — for now, run these to see it work.

cell 5 · write the dataset
import json
SYS = ("Write one social post as strict JSON with keys: "
       "hook, body, cta, hashtags. Warm, second-person, treats the "
       "reader as a skilled professional. Only use facts in the input.")

gold = [
 {"inp":'{"brand":"Brightpath","angle":"fair pay","pay_hours":48}',
  "out":'{"hook":"Your work. Your rate. Your call.","body":"Take the cases that fit your week and keep your full rate — no cut taken. Paid within about 48 hours.","cta":"Join the waitlist","hashtags":["#brightpath"]}'},
 {"inp":'{"brand":"Brightpath","angle":"fast pay","pay_hours":24}',
  "out":'{"hook":"Finish today. Paid tomorrow.","body":"No chasing anyone for money you already earned. Your payout lands within about 24 hours of the visit.","cta":"Join the waitlist","hashtags":["#brightpath"]}'},
 {"inp":'{"brand":"Brightpath","angle":"choose your work","pay_hours":48}',
  "out":'{"hook":"You decide what. You decide when.","body":"Browse cases and pick only the ones that fit your life. Full rate, no cut, paid within about 48 hours.","cta":"Join the waitlist","hashtags":["#brightpath"]}'},
]
with open("gold.jsonl","w") as f:
    for r in gold:
        f.write(json.dumps({"instruction":SYS,"input":r["inp"],"output":r["out"]})+"\n")
print("wrote", len(gold), "examples")
◆ Why the same angle appears with different pay_hours

Examples 1 and 3 share an angle but pay_hours differs (48 vs 48) while example 2 uses 24 — the output number always matches its own input. That contrast is what teaches the model "pull the number from the input", not "memorise 48".

Part 4 · the payoff

Train it & watch the loss fall

Training is a loop: predict → measure how wrong (the loss) → nudge the overlay → repeat. You watch one number go down.

4

Run the training loop

~40 seconds on a T4
▸
cell 6 · train
from datasets import load_dataset
from trl import SFTTrainer, SFTConfig

ds = load_dataset("json", data_files="gold.jsonl")["train"]
def fmt(x):
    return {"text":
        f"<|im_start|>system\n{x['instruction']}<|im_end|>\n"
        f"<|im_start|>user\n{x['input']}<|im_end|>\n"
        f"<|im_start|>assistant\n{x['output']}<|im_end|>"}
ds = ds.map(fmt)

trainer = SFTTrainer(model=model, tokenizer=tok, train_dataset=ds,
    args=SFTConfig(per_device_train_batch_size=1, gradient_accumulation_steps=2,
        num_train_epochs=10, learning_rate=2e-4, logging_steps=1,
        output_dir="out", seed=42))
trainer.train()

▲ Look closely — it may now invent facts

On only 3 examples the model overfits: it learns the voice but may state a payout time or detail that was never in your input. Fluent and completely made up. That's not magic failing — it's the lesson in the next part.

Part 5 · do it properly

Why the toy hallucinates — and the real fix

You just saw a model that sounds right and may be factually wrong — the most dangerous kind of output, because it's believable. Two things cause it, and both are fixable.

Why did it invent facts after training?

Too little data. With 3 examples it couldn't learn "the fact comes from the input" — it only saw a few fact-shaped patterns and imitated their shape, filling in plausible-sounding numbers.

The fix: more varied examples where the same task appears with different input values, so the model learns the fact is a variable, not a constant.

How many examples, and how many epochs?

~150+ varied, human-approved examples, and 2–3 epochs (not 10). More data + fewer passes = learns the pattern instead of memorising specific posts.

Also hold out ~10% as a validation set the model never trains on. Training loss always falls; validation loss is the honest signal. When val loss starts rising while train loss keeps falling, you're overfitting — stop.

How do I build 150 examples without writing them all by hand?

Write ~10 truly gold examples yourself. Then have a frontier model draft more, giving it your gold ones as the voice reference — and you approve or edit every single one. The frontier model drafts; a human who knows the voice is the final judge. Nothing enters the dataset unapproved.

6

Add a validator (your safety net)

~30 lines, useful even without fine-tuning
▸

Never ship raw model output. This function fails a post on objective violations — invalid JSON, missing brand tag, or a fact that isn't in the config. Run it on every generation.

cell 8 · the validator
import json
def validate(raw, config):
    fails = []
    try: post = json.loads(raw)
    except: return False, ["invalid_json"]
    if set(post) != {"hook","body","cta","hashtags"}:
        fails.append("wrong_keys")
    if "#brightpath" not in [h.lower() for h in post.get("hashtags",[])]:
        fails.append("missing_brand_tag")
    # fact-leak: flag day/time words not grounded in config (starter heuristic)
    body = post.get("body","").lower()
    for w in ["monday","thursday","minute","week"]:
        if w in body: fails.append(f"possible_fact_leak:{w}")
    return (len(fails)==0), fails

bad = '{"hook":"x","body":"We pay out Thursday nights in 2 minutes.","cta":"Go","hashtags":["#brand"]}'
print(validate(bad, {"pay_hours":48}))
You should see
(False, ['missing_brand_tag', 'possible_fact_leak:thursday', 'possible_fact_leak:minute'])
◆ What just happened

Thirty lines of plain Python caught a fluent lie your eyes might have waved through. That's evaluation: mechanical, run on every output, never fooled by good-sounding copy. In production you'd also inject high-stakes facts via slots (so the model can't write them wrong) and add an LLM-as-judge grounding check.
